## Fixed during this audit

Four defects were found *in this branch's own new code* and fixed before the report closed.

1. **The "zero-loss" precision fixes were not zero-loss** (critical-path, CONFIRMED by
   execution). Two exemptions added earlier the same day silently passed credentials master
   caught:
   - `_is_dotted_reference` exempted *any* dotted value, so `PASSWORD=jonathan.smith` — a
     `name.surname` password — read as a forwarded attribute. Now requires the final segment
     to equal the assigned name, which is what makes it a *forwarding* pattern.
   - `_TYPE_ANNOTATION_VALUE_RE` matched a **prefix**, so `password: Path-2026-Xy9z-secretvals`
     and `api_key: int-8f2k1-zzz` slipped through — and **YAML, the dominant secrets-config
     format, uses `:` for every assignment.** Now anchored at both ends.

   Both are pinned by regression tests. This is the single most important result of the run:
   the coordinator had asserted zero loss twice, and was wrong.

2. **`(no local file access)` was false** on `engine review` and on `propose --agentic`
   (critical-path, CONFIRMED). Both run the read-only toolbox over the repo, so file
   contents *do* reach xAI. The note misdescribed the egress at the exact moment a human
   consents to a channel switch. Each path now states its real channel.

## Confirmed findings

### HIGH

**H1 · The secret gate's refusal is a self-serve unlock.** *(critical-path · fable;
converges with grok's independent critique — 2 vendors)* CONFIRMED.
`cli_doer.py:236-250` prints paste-ready `<digest>  <path>` lines, and `cli_doer.py:186-195`
honours any manifest reachable from local `HEAD`. So the only human review of a suppression
happens *after* the egress it authorises — and egress is irreversible. No knowledge of the
value is needed; the gate computes the digest for you. The refusal text lands directly in a
coordinating agent's context, and at `supervised`/`autopilot` that agent can commit
unprompted. The stated control ("committed puts every suppression in front of a reviewer")
fires post-egress. **Constructive fix:** honour suppressions only when reachable from the
**default branch** (already human-reviewed), or add an interactive `cohort secrets declare`
instead of paste-ready lines. Tracked as #246.

**H2 · `my-office sync` reports success when IDE placement silently failed.**
*(ops · grok-4.5)* CONFIRMED by coordinator — `myoffice.py:260-263` catches bare `Exception`
and returns `[]`, and `recompiled: []` is the *same* signal as "nothing installed". Remote
layer current, local IDE artifacts stale, exit 0. Needs an explicit `recompile_failed`.

**H3 · Corrupt install manifest has no fail-closed load and no restore path.**
*(ops · grok-4.5)* REPORTED — cited `manifest.py:96-100`, `status.py:173`, `update.py:610`.
The manifest is "the source of truth a reverse replays"; quarantine fails closed but the
manifest does not, and there is no `doctor`/`repair`. Coordinator did not fault-inject.

**H4 · Default-allow code egress is documented nowhere a user will read.**
*(business-ops · fable)* CONFIRMED — `grep -rn 'cohort:egress'` finds the marker only in
source and the ledger; README names xAI/Grok nowhere. A user in an NDA repo ships source to
three vendors by default, with no README warning and no discoverable off-switch. The
default-allow policy lives in `canonical/commands/consult-grok.md`, visible only
post-install. **Cheapest 1.0.0 blocker on the list.**

**H5 · `tier` names three incompatible concepts.** *(naming · Codex)* CONFIRMED — install
scope (`global`/`project`), agent model class (`fast`/`default`/`top`, `agent.json:26`), and
engine model class (`flagship`/`cheap`/`reasoning`). A public CLI freezes its vocabulary at
1.0.0, so this is a rename-now-or-never item.

**H6 · Dashboard create-cards and the reload chip are keyboard-unreachable.**
*(accessibility · Codex)* CONFIRMED — `dashboard.js:219` `ghostCard()` builds a `<div>` with
a click listener and no `tabindex`, role, or key handler; `dashboard.html:326` is the same
pattern for the documented reload affordance.

### MED

- **G4 · HIGH — distribution is clone-only.** Install is `git clone` → venv → `pip install

  PyPI-name collision in #234 as unverifiable from inside the checkout — correct hygiene;

### Verified sound

- **Dependency licensing is clean.** Every runtime dep in `requirements.lock` is permissive
  (MIT / BSD / ISC), none copyleft, none vendored — so notices travel via package metadata
  and no third-party-notices file is needed at this distribution model.
- **No telemetry, no analytics, no phone-home, no accounts, no server.** A grep over `cli/`
  returns zero hits. This is what makes the "locally-run tool, not a processor" posture true,
  and it is worth re-verifying each run rather than inheriting.
- **A working security-disclosure channel exists** (`SECURITY.md`), and `GOVERNANCE.md` is
  unusually honest about its single-maintainer state.

### REQUIRES PROFESSIONAL OPINION

These are framed, not answered. An audit may identify and scope a legal question; it may not
resolve one, and a confident wrong answer here is the single most damaging thing this track
can produce — worse than silence.

**B1 · Default-allow egress without an in-product notice.**
*Question for counsel:* does distributing an MIT-licensed tool whose **default** behaviour
transmits user source — potentially containing personal data — to three named third parties
create exposure for the distributor, and does the MIT "as is" clause cover it?
*What makes it non-obvious:* the call runs on the user's machine with the user's own API keys
under the user's own vendor agreements, which is the substance of the distributor-not-processor
claim. But the **default** was a design decision made on the user's behalf.
*Cost of being wrong:* defending a claim with no notice artifact to point at.
*Since narrowed:* 0.15.0 added a README section naming what leaves the machine, to whom, per
command, plus the literal `cohort:egress=deny` marker — so the "no notice" half is largely
addressed. The design-choice half is not, and is the part for counsel.

**B2 · Inbound licensing of commits already merged.**
*Question for counsel:* is GitHub's ToS inbound=outbound default sufficient for the external
contributions already in the tree, or should retroactive sign-off be obtained?
*What changed:* 0.16.0 added a licensing paragraph to `CONTRIBUTING.md`, which stops the gap
growing but does nothing retroactive — and the tree now carries contributions from two
external users, merged before that text existed.
*Why 1.0.0 is the trigger:* a stable release is when history becomes what people rely on. The
realistic scenario is not a dispute; it is wanting to relicense or dual-license later and
having to chase contributors.

**B3 · Trademark clearance on the name.**
*Question for counsel:* a knockout search on "Cohort" for developer tools in the operating
jurisdiction — is the name defensible, or should 1.0.0 ship under a qualified mark?
*Why 1.0.0 is the trigger:* that is when the name accrues goodwill and when a conflict letter
becomes worth someone's time. For a CLI whose *command* is the brand, a post-1.0 rename breaks
every install script and every doc. Note the PyPI name is already held by an unrelated
multi-agent tool (#234).

### H1's first fix was an over-correction, and the audit's own recommendation was too blunt

The first cut made suppressions valid **only** from the default branch. It was verified to
re-break the exact thing this branch existed to fix: `cohort engine review grok` on cohort
refused again, because the manifest lived only on the feature branch. The same session
unblocked grok and then re-blocked it.

Separating the threat model explains why. A **hurried human** self-approving is only stopped
by a default-branch rule if *someone else* reviews — and `GOVERNANCE.md` documents a sole
maintainer with a self-merge exception, so for this repo it mostly adds delay. An **agent**
self-approving is the sharp case, and the one the finding actually named: the refusal prints
paste-ready lines *into the coordinating agent's context*, and at supervised/autopilot it can
commit and re-dispatch unprompted.

So the control's value is almost entirely against agents, while its cost falls almost
entirely on humans doing ordinary work. The rule now gates on **"is a human deciding right
now"** rather than **"has it merged"**, which is the same confirm-for-irreversible pattern
Cohort already applies elsewhere. Confirmation authorises *declared* fixtures only — a
credential nothing declares is never waved through at the prompt.

**Lesson for future runs:** a finding's recommended remedy is a claim to verify, exactly like
the finding itself. This one was adopted verbatim and shipped a regression that a single
end-to-end run caught immediately.

## What must be true for 1.0.0, and what is not

| Must be true | Status |
|---|---|
| A user can discover what leaves their machine, and how to stop it | **No** — H4 |
| A suppression cannot authorise its own egress | **No** — H1 |
| The public CLI vocabulary is stable and unambiguous | **No** — H5 |
| Durable state loads fail-closed or restores | **No** — H3 |
| A path claiming to place artifacts never reports all-clear when it failed | **No** — H2 |
| Partial engine failure is never success | **Half** — read path fixed, write path M1 |
| Every vendor path we advertise actually works | **No** — V1; grok is API-only |
| The dashboard is operable by keyboard | **No** — H6 |
| The egress audit trail survives concurrency | **No** — M6 |

**Bottom line.** The install/merge/trust core and the digest+path binding are genuinely well
built. What is not 1.0-ready is the *authorisation story* around the new manifest (H1), the
*disclosure* story around default-allow egress (H4), and the honesty of success signals
(H2, M1, V2). The cheapest two blockers — H4 and M9 — are documentation, not code.
